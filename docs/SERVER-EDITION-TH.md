## 1. เป้าหมาย

- มีเครื่อง Ubuntu หนึ่งเครื่อง (VM หรือ VPS) เปิด HR Auto ทิ้งไว้ตลอด
- สั่งงานจาก **มือถือ** ได้จากทุกที่ เช่น ตอนออกไปกินข้าวก็กดเริ่มคิวรอบเที่ยงได้
- โพสต์รอบละประมาณ 50 กลุ่ม วันละ 3 รอบ (เช้า กลางวัน เย็น)
- **ไม่กระทบเวอร์ชัน Windows เดิม** ทั้งโค้ดและข้อมูล

## 2. ทำไมเอาเวอร์ชันเดิมไปรันบนเซิร์ฟเวอร์ตรง ๆ ไม่ได้

| ปัญหาในเวอร์ชันเดิม | ผลบนเซิร์ฟเวอร์ | แก้ในเวอร์ชันนี้ |
|---|---|---|
| ตัวกันแรมหยุดเปิดแท็บเมื่อ RAM ว่างต่ำกว่า **4 GB** (ฝังในโค้ด) | VPS 2–4 GB มี RAM ว่างไม่ถึง 4 GB ตลอด → คิว **ค้างพักตลอดกาล** | ปรับได้ด้วย `HR_AUTO_MIN_FREE_MEMORY_MB` / `HR_AUTO_MIN_FREE_MEMORY_RATIO` (ไม่ตั้ง = 4 GB เหมือนเดิม) |
| บน Linux อ่าน RAM ว่างจาก `os.freemem()` | อาจนับแคชของระบบเป็น "ใช้แล้ว" ทำให้ดูเหมือนแรมเต็มทั้งที่ยังว่าง | อ่าน `MemAvailable` จาก `/proc/meminfo` ตรง ๆ |
| Chromium ต้องมีหน้าจอ | VPS ไม่มีจอ เปิด Chromium ไม่ขึ้น | จอเสมือน **Xvfb** + ตัวจัดหน้าต่าง **openbox** |
| ล็อกอิน Facebook / แก้ Checkpoint ต้องทำในหน้าต่าง Chromium | มองไม่เห็นหน้าต่างบนเซิร์ฟเวอร์ | **noVNC** ดูและกดหน้าจอ Browser ผ่านเว็บ (มือถือก็ได้) |
| หน้าเว็บบังคับกว้างขั้นต่ำ 960px | ใช้บนมือถือต้องซูมไปมา | เพิ่มเลย์เอาต์มือถือ (ต่ำกว่า 760px เมนูเป็นแถบเลื่อนด้านบน การ์ดเรียงแถวเดียว) |
| แอปรับเฉพาะ `127.0.0.1` และไม่มีระบบล็อกอิน | เปิดออกเน็ตตรง ๆ = ใครก็สั่งโพสต์ด้วยบัญชีคุณได้ | **ไม่เปิดออกเน็ต** ใช้ SSH tunnel หรือ **Tailscale** (เฉพาะอุปกรณ์ของคุณ) |
| ต้องเปิดหน้าต่าง PowerShell ค้างไว้ | ปิด SSH แล้วโปรแกรมตาย | รันเป็น **systemd service** เปิดเองตอนบูต ล่มแล้วรีสตาร์ทเอง |
| ไม่มีฟอนต์ไทยใน Ubuntu Server | หน้า Facebook และภาพหลักฐานเป็นสี่เหลี่ยม | ลง `fonts-thai-tlwg` + Noto |

## 3. ภาพรวมสถาปัตยกรรม

```text
 มือถือ / คอม (ที่ไหนก็ได้)
   │  Tailscale (เข้ารหัส เฉพาะอุปกรณ์ในบัญชีคุณ)  หรือ  SSH tunnel
   ▼
┌──────────────────────────── Ubuntu (VM / VPS) ────────────────────────────┐
│                                                                            │
│  tailscale serve :443  ──►  HR Auto (node, 127.0.0.1:4173)  ← hr-auto      │
│                                  │ Playwright                              │
│                                  ▼                                         │
│                             Chromium (headed)                              │
│                                  │ วาดบน                                    │
│                                  ▼                                         │
│                     Xvfb :99 (จอเสมือน 1366x900) + openbox                  │
│                                  │                                         │
│  tailscale serve :8443 ──►  noVNC/websockify (127.0.0.1:6080)              │
│                                  └─► x11vnc (127.0.0.1:5900, มีรหัสผ่าน)     │
│                                                                            │
│  ข้อมูล: /var/lib/hr-auto (chmod 700)   โปรแกรม: /opt/hr-auto               │
│  ตั้งค่า: /etc/hr-auto/hr-auto.env                                           │
└────────────────────────────────────────────────────────────────────────────┘
```

ทุกพอร์ตฟังแค่ `127.0.0.1` ไม่มีพอร์ตไหนเปิดออกอินเทอร์เน็ตโดยตรง

### ทำไมใช้ Chromium แบบมีหน้าจอ (headed) ไม่ใช้ headless

- Facebook ตรวจจับ browser แบบ headless ได้ง่ายกว่า เสี่ยงโดน Checkpoint มากขึ้น
- ต้องมีหน้าจอให้คุณล็อกอิน ทำ 2FA และแก้ Checkpoint เองอยู่แล้ว
- พฤติกรรมเหมือนเวอร์ชัน Windows ที่ทดสอบมาแล้วมากที่สุด
- ค่าใช้จ่ายเพิ่มน้อย Xvfb + x11vnc + noVNC ใช้ RAM รวมประมาณ 50–100 MB

### คิวไม่ค้างอีก: ลองใหม่ท้ายคิว

**อาการเดิม:** ในโหมดโพสต์อัตโนมัติ บางกลุ่มค้างที่ "รอยืนยัน" ตลอด และกินช่องแท็บไว้จนต้องปิดแท็บเอง

**สาเหตุ:** ระบบตั้งนาฬิกาครั้งเดียวต่อแท็บ (สุ่ม 8–150 วินาที) ถ้านาฬิกาดังตอนคิว "พัก" อยู่ (เช่น ระบบพักเองเพราะโพสต์พลาด 2 ครั้งติด หรือคุณกดพัก) หรือแท็บไม่ว่าง หรือคำสั่งพัง นาฬิกานั้นจะเลิกไปเลย กดทำต่อแล้วแท็บนั้นก็ไม่ถูกโพสต์อีก (พิสูจน์แล้ว: ทดสอบเดียวกัน โค้ดเดิมค้าง โค้ดใหม่จบครบ)

| | ตอนนี้ |
|---|---|
| ตัวโพสต์อัตโนมัติ | ตัวเฝ้าคิวตรวจทุก 1 วินาที โพสต์แท็บที่ถึงเวลา **ทีละแท็บ** เว้นช่วงสุ่มระหว่างโพสต์ (อย่างน้อย 8–16 วินาที) พัก/ไม่ว่างก็แค่รอรอบถัดไป ไม่ทิ้งงาน |
| โพสต์อัตโนมัติพังก่อนกด Post | ปิดแท็บ แล้ว**ย้ายกลุ่มไปลองใหม่ท้ายคิว**อัตโนมัติ |
| เปิดกลุ่มไม่ขึ้น / หาช่องโพสต์ไม่เจอ / หมดเวลา ตอนเตรียมโพสต์ | ย้ายไปลองใหม่ท้ายคิว 1 ครั้ง (`HR_AUTO_MAX_AUTO_REQUEUES`) ถ้ายังไม่ได้ค่อยนับว่าไม่สำเร็จ |
| ปุ่ม **↻ ไปท้ายคิว** (กลุ่มที่รอยืนยัน) | ปิดแท็บ ย้ายไปท้ายคิว แท็บว่างให้กลุ่มถัดไปทันที ไม่มีโพสต์ซ้ำเพราะยังไม่ได้กด Post |
| ปุ่ม **↻ ลองใหม่ท้ายคิว** (กลุ่มที่ต้องตรวจ/ไม่สำเร็จ ขณะคิวทำงาน) | ใช้หลังตรวจ Facebook แล้วว่ายังไม่มีโพสต์ |

**สิ่งที่ระบบจงใจไม่ลองใหม่เอง** เพื่อกันโพสต์ซ้ำ: กลุ่มที่กด Post ไปแล้วแต่ผลไม่ชัด, แท็บที่คุณปิดเอง (อาจโพสต์เองไปแล้ว), เจอ Checkpoint/CAPTCHA หรือ Browser ถูกปิด

## 5. ตัวแปรใหม่

| ตัวแปร | ค่าเริ่มต้น (ไม่ตั้ง) | ค่าในไฟล์ตัวอย่างของเซิร์ฟเวอร์ | หน้าที่ |
|---|---|---|---|
| `HR_AUTO_MIN_FREE_MEMORY_MB` | `4096` | `600` | พักเปิดแท็บใหม่เมื่อ RAM ที่ใช้ได้ต่ำกว่าค่านี้ (MB) |
| `HR_AUTO_MIN_FREE_MEMORY_RATIO` | `0.12` | `0.10` | พักเปิดแท็บใหม่เมื่อ RAM ที่ใช้ได้ต่ำกว่าสัดส่วนนี้ของ RAM ทั้งหมด |
| `HR_AUTO_MAX_AUTO_REQUEUES` | `1` | `1` | จำนวนครั้งที่กลุ่มซึ่งพังก่อนกด Post จะถูกย้ายไปลองใหม่ท้ายคิว (0 = ไม่ลองใหม่) |
| `HR_AUTO_BROWSER_ARGS` | ว่าง | `--window-size=1366,900` | argument เพิ่มให้ Chromium คั่นด้วยช่องว่าง |
| `HR_AUTO_REMOTE_VIEW_URL` | `http://{host}:6080/vnc.html?...` เมื่อมี `DISPLAY` | ตั้งโดย `tailscale-setup.sh` | ลิงก์ของปุ่ม "ดูหน้าจอ Browser" `{host}` = ชื่อโฮสต์ที่ใช้เปิด HR Auto |

ค่าที่ใส่ผิด (ไม่ใช่ตัวเลข หรือติดลบ) จะกลับไปใช้ค่าปลอดภัย 4 GB / 12% ไม่ได้ปิดตัวกันแรม

## 6. ทดสอบใน VM (VMware, Ubuntu)

VM ของคุณ: RAM 4 GB, 2 CPU, ดิสก์ 20 GB, Network แบบ NAT ใกล้เคียงแพ็กเกจ SSD2 (590 บาท) ใช้ทดสอบได้พอดี

### 6.1 เตรียม VM

1. เปิด VM แล้วเข้า Terminal
2. เช็กพื้นที่ว่าง ต้องเหลืออย่างน้อย ~4 GB:
   ```bash
   df -h /
   ```
3. ถ้ายังไม่มี git:
   ```bash
   sudo apt update && sudo apt install -y git
   ```

### 6.2 ติดตั้ง

```bash
git clone -b server-edition https://github.com/PleaseCompile/HR_Auto_Post_FB.git
cd HR_Auto_Post_FB
sudo bash deploy/ubuntu/install.sh
```

ใช้เวลาประมาณ 5–15 นาที (โหลด Node.js, Chromium และแพ็กเกจระบบ) จบแล้วจะขึ้น ✅ พร้อมวิธีเข้าใช้งาน

### 6.3 เข้าใช้งานจากเครื่อง Windows (ผ่าน SSH tunnel)

ใน VM ดู IP:

```bash
hostname -I
```

บน Windows เปิด PowerShell (ใช้พอร์ต 14173 เพราะ HR Auto ตัวเดิมบน Windows ใช้ 4173 อยู่):

```powershell
ssh -N -L 14173:127.0.0.1:4173 -L 6080:127.0.0.1:6080 <ชื่อผู้ใช้ใน VM>@<IP ของ VM>
```

เปิดหน้าต่างนี้ค้างไว้ แล้วเปิดเบราว์เซอร์บน Windows:

- HR Auto: <http://127.0.0.1:14173>
- หน้าจอ Browser (noVNC): <http://127.0.0.1:6080/vnc.html?autoconnect=1&resize=scale>
  รหัสผ่าน: ใน VM รัน `sudo cat /etc/hr-auto/vnc-password.txt`

### 6.4 ล็อกอิน Facebook ครั้งแรก

1. เปิดหน้า noVNC ทิ้งไว้แท็บหนึ่ง
2. ใน HR Auto ไป `ตั้งค่าและ Session` → กด `เชื่อมต่อ Facebook`
3. หน้าต่าง Chromium จะโผล่ในหน้า noVNC → ล็อกอินและทำ 2FA ในนั้น
4. กลับไปหน้า HR Auto กด `ตรวจ Session` ต้องขึ้น "พร้อมใช้งาน"

> โปรไฟล์ Facebook จาก Windows **ก๊อปมาใช้ไม่ได้** (DPAPI ดู [FACEBOOK-SESSION-EXPLAINED-TH.md](FACEBOOK-SESSION-EXPLAINED-TH.md)) ต้องล็อกอินใหม่บนเครื่องนี้

### 6.5 ทดสอบจากมือถือ (Tailscale)


1. เปิดลิงก์ที่ขึ้นมาเพื่อล็อกอิน Tailscale (สมัครฟรีด้วยบัญชี Google ได้)

4. ถ้าเปิดไม่ได้: ใน Tailscale admin console → DNS → เปิด **MagicDNS** และ **HTTPS Certificates**

## 7. ขึ้นเซิร์ฟเวอร์จริง (Ubuntu 26, 1 core / 2 GB, โดเมน wanlaza.com)

เป้าหมาย: ทีม 4 คนเปิด `https://hr.wanlaza.com` จากมือถือที่ไหนก็ได้ ใช้**รหัสผ่านทีมเดียวกัน** สิทธิ์เท่ากันทุกคน และทุกคนควบคุมหน้าจอ Browser ได้

### 7.1 ภาพรวม

```text
มือถือทีม ── https://hr.wanlaza.com ──► VPS (IP เปิดเผย, firewall เปิดแค่ 22/80/443)
                                         Nginx (HTTPS จาก Let's Encrypt, จำกัดการลองรหัส)
                                           ├─ ทุกหน้า → HR Auto (127.0.0.1:4173) ต้องล็อกอินรหัสทีม
                                           └─ /vnc/  → noVNC (127.0.0.1:6080) Nginx ถาม HR Auto ก่อนว่าล็อกอินแล้วไหม
```

### 7.2 สิ่งที่ปรับให้เหมาะกับ 1 core / 2 GB

| เรื่อง | ทำอะไร | ทำไม |
|---|---|---|
| จำนวนแท็บ | แนะนำ 2 แท็บ, ปิดโหมดหลายหน้าต่าง | วัดจริงใน VM: ระบบ + Chromium 1 แท็บ ≈ 1.2 GB เหลือที่ให้อีกแท็บเดียว |
| Chromium | ปิด GPU, ปิดวิดีโอเล่นเอง, ปิด extension/ตัวอัปเดต, จำกัด process | ลด CPU/RAM ที่ Feed ของ Facebook กิน |
| จอเสมือน | 1280x800 | framebuffer และภาพที่ส่งให้คนดูเล็กลง |
| VNC | x11vnc ตรวจจอทุก 50 ms (เดิม 20 ms) | คนดูพร้อมกัน 4 คนไม่แย่ง CPU กับ Facebook มากเกินไป |
| RAM เต็ม | zram (swap บีบอัดในแรม) + swap ดิสก์ 1 GB, ตัวโปรแกรมตั้ง OOM -500 และดัน Chromium เป็น +600 | ถ้าแรมหมด เคอร์เนลจะฆ่าแท็บ ไม่ใช่ตัวโปรแกรม |
| Chromium ล่ม | แท็บที่ยังไม่ได้กด Post ย้ายไปลองใหม่ท้ายคิว แล้วเปิด Browser ใหม่เอง | คิวไปต่อได้โดยไม่ต้องมีคนเฝ้า |
| ดิสก์ 20 GB | ลบภาพหลักฐานของระบบที่เก่ากว่า 60 วัน และลบเก่าสุดก่อนถ้าพื้นที่เหลือ < 2 GB (ไม่แตะไฟล์ที่ทีมอัปโหลดเอง) | ภาพหลักฐานสะสมวันละหลายสิบ MB |
| log | journald สูงสุด 200 MB, browser-events และ audit หมุนไฟล์ที่ 5 MB | log ไม่กินดิสก์ |
| สำรองข้อมูล | ทุกคืน 03:30 เก็บฐานข้อมูล รูป Draft และบันทึกกิจกรรม 14 วัน ที่ `/var/backups/hr-auto` | กู้คืนได้ถ้าเครื่องพัง (ไม่สำรอง Session Facebook โดยตั้งใจ) |

### 7.3 ความปลอดภัย

| ชั้น | รายละเอียด |
|---|---|
| ล็อกอินทีม | รหัสเดียว ≥ 10 ตัว เก็บแค่ค่า scrypt hash, จำเครื่องไว้ 30 วัน, เปลี่ยนรหัส = ทุกเครื่องถูกออกจากระบบ |
| กันเดารหัส | ผิด 5 ครั้งใน 15 นาที → ล็อกเฉพาะ IP นั้น, Nginx จำกัด 10 ครั้ง/นาที/IP |
| กันเว็บอื่นสั่งงาน | cookie `SameSite=Strict` + ตรวจ Origin ทุกคำสั่งที่เปลี่ยนข้อมูล |
| หน้าจอ Browser | เข้า `/vnc/` ได้เฉพาะคนที่ล็อกอินแล้ว (Nginx `auth_request`) ไม่มีรหัส VNC แยก |
| บันทึกกิจกรรม | ใครทำอะไร จาก IP ไหน ดูได้ในหน้าตั้งค่า (ใส่ชื่อตอนล็อกอิน) |
| เครือข่าย | ตัวแอปและ VNC ฟังแค่ 127.0.0.1, firewall เปิดแค่ SSH (จำกัดอัตรา), 80, 443 |
| HTTPS | Let's Encrypt ต่ออายุอัตโนมัติ, HSTS |

**แนะนำมาก:** ใช้ SSH key แทนรหัสผ่าน SSH (IP ของ VPS เปิดเผย มีบอตเดารหัส SSH ตลอดเวลา) ตั้ง key ให้เข้าได้ก่อน แล้วค่อยปิดรหัสผ่านใน `/etc/ssh/sshd_config` (`PasswordAuthentication no`) ตัวติดตั้ง**ไม่**ปิดให้เอง เพราะถ้ายังไม่มี key จะเข้าเครื่องไม่ได้อีกเลย

### 7.4 ขั้นตอน

1. **เช่า VPS** Ubuntu 26.04 แล้วจด IP
2. **ตั้ง DNS ใน Cloudflare** → wanlaza.com → DNS → Records → Add record

   | Type | Name | IPv4 address | Proxy status |
   |---|---|---|---|
   | `A` | `hr` | IP ของ VPS | **DNS only (เมฆสีเทา)** |

3. **SSH เข้า VPS แล้วติดตั้ง**
   ```bash
   sudo apt update && sudo apt install -y git
   git clone -b server-edition https://github.com/PleaseCompile/HR_Auto_Post_FB.git
   cd HR_Auto_Post_FB && sudo bash deploy/ubuntu/install.sh
   ```
   ตัวติดตั้งจะถาม:
   - Access mode → `1` (public)
   - Domain → `hr.wanlaza.com`
   - Email → สำหรับแจ้งเตือนใบรับรองใกล้หมดอายุ
   - ยอมรับเงื่อนไข Let's Encrypt → `yes`
   - **รหัสผ่านทีม** (พิมพ์ 2 ครั้ง ไม่แสดงบนจอ)
4. **เปิด `https://hr.wanlaza.com`** ล็อกอิน → ตั้งค่าและ Session → เชื่อมต่อ Facebook → ปุ่ม "ดูหน้าจอ Browser" → ล็อกอิน Facebook + 2FA
5. **ตรวจทั้งระบบ:** `sudo bash deploy/ubuntu/doctor.sh`

ทดสอบก่อนใน VM ได้ด้วยโหมด `2` (lan): http ธรรมดาที่พอร์ต 80 ใช้ระบบล็อกอินกับ Nginx แบบเดียวกัน ยกเว้น HTTPS (ใช้ทดสอบเท่านั้น ห้ามเปิดออกอินเทอร์เน็ต)

### 7.5 ข้อควรรู้

- **ล็อกอิน Facebook จาก IP ของ Data Center** Facebook มักขอยืนยันตัวตนครั้งแรก ทำผ่านหน้าจอ Browser ด้วยตัวเอง และอย่าใช้หลายบัญชีบนเครื่องเดียว
- **ทุกคนคุมเมาส์ได้พร้อมกัน** ตกลงกันในทีมว่าใครกำลังใช้หน้าจอ Browser อยู่ ไม่อย่างนั้นจะกดแย่งกัน
- โฟลเดอร์ `/var/lib/hr-auto/browser-profile` บน Linux **ไม่ได้เข้ารหัสแบบ DPAPI** ป้องกันด้วยสิทธิ์ไฟล์ (`chmod 700`) เท่านั้น ห้ามให้คนอื่นมีสิทธิ์ root บนเครื่องนี้
- 1 core / 2 GB คือขั้นต่ำ: คาดว่า 50 กลุ่มใช้ราว 30–45 นาทีต่อรอบ (ประมาณการ) ถ้าต้องการเร็วขึ้น อัปเกรดเป็น 4 GB / 2 core ได้ผลมากกว่าแก้โค้ด

## 11. ข้อจำกัดที่รู้อยู่แล้ว

- ถ้า HR Auto รีสตาร์ทกลางคิว (อัปเดต, เครื่องรีบูต, โปรแกรมล่ม) คิวจะเปลี่ยนเป็นสถานะ `interrupted` และกลุ่มที่กำลังเตรียมหรือกำลังส่งอยู่ตอนนั้นจะเป็น "ต้องตรวจเอง" (`manual_action_required`) ระบบจงใจไม่วิ่งต่อเอง ให้ตรวจใน Facebook ก่อนว่ากลุ่มเหล่านั้นโพสต์ไปแล้วหรือยัง แล้วค่อยกดทำต่อ เพื่อกันโพสต์ซ้ำ
- โหมด **หลายหน้าต่าง** ไม่ปิดแท็บเอง ไม่เหมาะกับเครื่อง RAM 4 GB ให้ใช้ **Hybrid** 3–4 แท็บ
- ยังไม่มีระบบแจ้งเตือนเข้ามือถือ (เช่น คิวพักเพราะเจอ Checkpoint) ต้องเปิดหน้าเว็บดูเอง
- ยังไม่มีระบบตั้งเวลาให้คิวเริ่มเอง ต้องกดเริ่มจากมือถือ
- ยังไม่ได้ทดสอบบนเครื่องจริง ผลทดสอบใน VM ของคุณคือการยืนยันครั้งแรก
